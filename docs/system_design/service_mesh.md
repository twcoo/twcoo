# Service Mesh

## Sidecar Proxies, Transparent Retries, and Idempotency

Why service-to-service traffic needs the same solutions as client-to-server traffic: In a microservices system, any service calling another (e.g., Order calling Payment) faces the same problems a client faces calling a load-balanced backend, which instance to call, whether that instance is healthy, and how to retry safely on failure.

### Sidecar Proxy

Rather than routing all inter-service traffic through once central load balancer, the routing/health-check/retry logic is handled by a small local helper deployed alongside each individual service instance. This helper parses outgoing requests, runs health checks against the destination service's instances, selects a healthy one, and routes the request transparently, so the calling service's application code never handles IP's or load-balancing logic directly, it simply issues a call to "Payment" (by name) and the sidecar does the rest. The full network of these per-instance helpers across a system is called a service mesh.

### Transparent retries

Retry logic (timeout handling, retry attempts, choosing a different healthy instance) belongs in the sidecar, not the calling service's application code, putting it in the application code reintroduces the complexity the sidecar exists to remove. On failure, the sidecar can silently retry against another healthy instance, the calling service only sees the final outcome.

### Idempotency Keys For Safe Retries

Automatic retries risk duplicate side effects (e.g., double charging a customer) if a request actually succeeded but its response was lost before the retry fired. The fix, make the operation itself safe to repeat, rather than trying to know for certain whether the first attempt succeeded.

- The Idempotency key must be generated once, before any retries occur, and reused identically across every retry of that logical request, a fresh key per retry defeats de-duplication entirely.

- The key should be generated by calling service (e.g., Order), since it has the contextual details (customer, order) needed to construct a stable, meaningful key.

- The duplicate check belongs to the receiving service (e.g., Payment), since it's the one actually performing the effect and owning the data store where the operation is recorded, the same role a durable table with a unique constraint plays in any idempotent-write design.

### Full flow

Calling service generates an idempotency key once -> passes it to its sidecar -> sidecar routes to a healthy instance of the target service -> on failure/timeout, sidecar retries automatically with the same key -> receiving service checks the key against its own store and safely no-ops on true duplicates.
