# Replication And Sharding

Replication is the practice of keeping copies of the same data on multiple nodes. It exists to solve three problems that a single database node cannot: read scaling (spreading read load across machines), availability (serving reads and surviving the loss of node), and failover (continuing to accept writes when the primary node dies). Replication does not help with capacity. Each replica holds the full dataset, so total storage consumed increases, and no single node's burden shrinks.

Leader-follower replication is the most common model. One node, the leader, accepts all writes. One or more followers received a stream of changes from the leader and apply them in order. Followers can serve reads and can be promoted to leader if the leader fails. The stream of changes is called the replication log, and each changes has a position called a log sequence number of LSN. Two nodes can compare LSNs to find the last point at which their histories agree.

The acknowledgement decision defines the replication mode. In asynchronous replication, the leader writes locally and immediately replies success to the client, shipping the change to followers afterward. This is fast but means an acknowledged write can be lost if the leader dies before propagating it. In synchronous replication, the leader waits for one or more followers to confirm the change before replying. This is safer but slower, or majority, replication is the middle ground: the leader waits for a majority of nodes to hold the write before replying.

Replication is inseparable from CAP. CAP does not mean "pick two of three always." It means that when a network partition occurs, the system must either refuse to serve on the side that cannot coordinate a majority (sacrificing availability on that side, preserving consistency) or allow both sides to serve (sacrificing consistency, accepting divergence). A system that requires a majority to accept writes is CP: during a 1 versus 2 partition, the lone node refuses writes and only the majority side services.

The loss of acknowledged writes is the central danger of asynchronous replication combined with automatic failover. If the leader acknowledged a write that has not reached a follower, then dies or partitioned away, a new leader is elected that never saw the write. When the old leader rejoins, it's divergent history, everything after the last common LSN, is discarded in favor of the new leader's history. The acknowledged write is gone. It is not merged, because merging would require conflict resolution against writes the new leader produced during the partition, which is often impossible to do correctly.

The fix is to change when the leader is allowed to acknowledged. If the leader refuses to confirm a write until majority of nodes hold it on disk, then any future majority that elects a new leader must overlap with that acknowledging majority. In a three node cluster, two majorities must share at least one node, and that shared node carries the write forward. This eliminates lost acknowledged writes without any merging. The cost is real: every write waits for a network round trip, and if too many nodes are down to form a majority, the system stops accepting writes.

There is no configuration that provides low latency, high availability, and no lost acknowledge writes simultaneously. Every production system is a deliberate point in this spectrum.

Sharding, also called partitioning, splits data across nodes so that no single node must hold all of it. Where replication gives copies, sharding gives divisions. A sharded table assigns each row to a shard based on one column, the shard key. The shard key is a single choice that governs the whole table, not a per-query decision.

The shard key determines which queries are cheap and which are expensive. If the key is customer_id, then "all orders for customer X" resolves to one shard because those rows share a customer_id, while "all orders on date Y" touches every shard because those orders belong to many customers. If the key is order_id, then single-order lookups are cheap but "all orders for customer X" spreads across shards. No shard key makes all access patterns fast. Choosing one optimizes some queries at the direct expense of others.

A query that cannot be routed to single shard becomes a scatter-gather, or fan out: it sent to every shard, each shard returns it's matching rows, and the results are merged. If the query sorts or limits, the merge must reorder or re-slice the combined rows, because each shard only saw its own slice. Cross-shard queries therefore pay a latency and coordination cost that single-shard queries are not.

## Choosing Shard Key

The shard key is the column that determines how rows of a distributed table are placed across shards. It is a single choice that governs the whole table. The shard ID, by contrast, is not something a user chooses; Citus assigns it from a cluster-wide counter when it creates each shard, and it serves only as a label on the resulting physical table. The decision that matters is the shard key, because it controls both query routing and load distribution at the same time.

Query routing follows from the shard key. A query filtered on the shard key hashes that value to a single shard and is answered by one node, which is the fast path. A query without a filter on the shard key cannot be routed to one shard, so it becomes a scatter-gather, sent to every shard and merged by the coordinator. The coordinator's EXPLAIN output makes this visible: a single-shard query shows a task count of one and names exactly one worker, while a fan-out query shows a task count equal to the total number of shards.

The first criterion is to match the dominant access pattern. The most frequent and most latency-sensitive query should filter on the shard key so it collapses to a single shard. Choosing a key optimizes the queries that use it and forces every other query to fan out. The question to answer is always which access pattern cannot afford to scatter-gather.

The second criterion is sufficient cardinality. The hash function spreads keys uniformly in expectation, but with few distinct keys the per-shard row counts vary widely. A low-cardinality key, such as a status or country column where most rows share a few values, produces severe skew: one shard hold nearly all the data and the rest sit idle, rebuilding a single-node database with extra machinery. High-cardinality keys with roughly even usage, such as a customer ID or order ID, distribute better.

The third criterion is avoiding hot data. Even a high-cardinality key can concentrate traffic if a few values dominate the workload, which is distinct from dominating the row count. A single very large customer whose orders all hash to one shard creates a hot shard that absorbs disproportionate traffic while row counts may look balanced. The concern is not only whether data distributes evenly but whether traffic distributes evenly. Mitigations include choosing a finer key, accepting fan-out for the heavy case, or using a compound key that splits the hot dimension.

The fourth criterion is co-location. Tables that are almost always joined together should be sharded on the same key so the join happens within a shard rather than across shards. A cross-shard join requires the coordinator to bring data together and is far more expensive than a local join. Co-location is a design property that must be chosen deliberately.

The fifth criterion is growth and rebalancing. A key that distributes well today can skew as a value distribution changes. Rebalancing is easier with many small shards than with a few large ones, which is why Citus defaults to a relatively high shard count even for small tables: finer granularity gives the rebalancer more to work with and let shards be added later without a full reshuffle.

The practical procedure follows from these criteria. First, list the queries that must be fast and identify the column they filter on or join on; that column is the strongest candidate. Second, check it's cardinality and the skew of both row counts and traffic, rejecting low-cardinality or hot-value columns. Third, check whether related tables need to be queried together and pick a key that allows co-location. Fourth, accept that the remaining queries will fan out and confirm that is acceptable for them.

A note on measurement. Per-shard counts reveal distribution and skew, but only when measured as rows. The citus_shards shard_size columnreports on-disk size in bytes, dominated at small data volumes by page allocation and index overhead, so it does not reflect row counts and should not be used to judge skew. True per-shard row counts come from counting rows in each physical shard table on the workers.

## Cross-Shard Joins and Co-Location

The lab cluster is a Citus coordinator with two worker nodes, citus-worker-1 and citus-worker-2, all in the namespace replication-and-sharding. The orders table has 1000 rows and is distributed by customer*id across 32 shards, placed round-robin so each worker holds 16. Shard IDs run from `orders_102008` to `orders_102039`, and the number after orders* is the Citus-assigned shard ID, drawn from a cluster-wide counter. The physical shard tables are real tables with real rows on the workers, and they are hidden from the default psql table listing, so they must be found by querying pg_class directly or by using the Citus shard views on the worker.

The experiment set up an order_items table deliberately sharded on a different key from orders. It was created with a primary key on (order_id, id), which satisfies the Citus rule that the primary key include the shard key, and distributed with `create_distributed_table('order_items', 'order_id')`. So orders is placed by customer_id and order_items is placed by order_id. The two table are not co-located.

The query under test joined the two tables on `i.order_id = o.id`, filtered by `o.customer_id = 42`. Running `EXPLAIN` on it produced the error `the query contains a join that requires repartitioning` with the hint to enable `citus.enable_repartition_joins`. Citus refuses this join by default because if cannot be answered shard-locally. The join key `order_id` matches `order_items` placement key but not orders placement key, and the `customer_id` filter matches orders placement key but gives no information about where the matching order_items rows live. So the coordinator would have to redistribute data across the network to complete the join.

The cost his reveals is the whole point of the experiment. Even though the query filtered to a single customer, the order_items side had to read all 32 shards, because order_id does not correspond to the customer_id placement. Every row from those shards was then re-hashed and shipped across the network into the temporary merged shards, and the joined results were shipped back to the coordinator for final assembly. A query that a co-located layout would answer by reading one shard and joining locally instead read every shard on one side and moved all of it's rows across the network. The client still receives a correct answer, but the work done to produce it is disproportionate to the size of the result.

A note on the mechanism, observed directly. A filter on the shard key, like `customer_id = 42`, routes to one shard by hashing the literal value and finding which shard's range in `pg_dist_shard` contains that hash, the finding the worker in `pg_dist_placement`. A filter on any other column, like amount > 50, gives Citus no value to has into the placement map, so it cannot narrow and becomes a scatter-gather. This is why the orders side of the join could narrow to one shard while the order_items side could not narrow at all: customer_id is a placement key, order_id is not.
