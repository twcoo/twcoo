# Replication And Sharding

Replication is the practice of keeping copies of the same data on multiple nodes. It exists to solve three problems that a single database node cannot: read scaling (spreading read load across machines), availability (serving reads and surviving the loss of node), and failover (continuing to accept writes when the primary node dies). Replication does not help with capacity. Each replica holds the full dataset, so total storage consumed increases, and no single node's burden shrinks.

Leader-follower replication is the most common model. One node, the leader, accepts all writes. One or more followers received a stream of changes from the leader and apply them in order. Followers can serve reads and can be promoted to leader if the leader fails. The stream of changes is called the replication log, and each changes has a position called a log sequence number of LSN. Two nodes can compare LSNs to find the last point at which their histories agree.

The acknowledgement decision defines the replication mode. In asynchronous replication, the leader writes locally and immediately replies success to the client, shipping the change to followers afterward. This is fast but means an acknowledged write can be lost if the leader dies before propagating it. In synchronous replication, the leader waits for one or more followers to confirm the change before replying. This is safer but slower, or majority, replication is the middle ground: the leader waits for a majority of nodes to hold the write before replying.

Replication is inseparable from CAP. CAP does not mean "pick two of three always." It means that when a network partition occurs, the system must either refuse to serve on the side that cannot coordinate a majority (sacrificing availability on that side, preserving consistency) or allow both sides to serve (sacrificing consistency, accepting divergence). A system that requires a majority to accept writes is CP: during a 1 versus 2 partition, the lone node refuses writes and only the majority side services.

The loss of acknowledged writes is the central danger of asynchronous replication combined with automatic failover. If the leader acknowledged a write that has not reached a follower, then dies or partitioned away, a new leader is elected that never saw the write. When the old leader rejoins, it's divergent history, everything after the last common LSN, is discarded in favor of the new leader's history. The acknowledged write is gone. It is not merged, because merging would require conflict resolution against writes the new leader produced during the partition, which is often impossible to do correctly.

The fix is to change when the leader is allowed to acknowledged. If the leader refuses to confirm a write until majority of nodes hold it on disk, then any future majority that elects a new leader must overlap with that acknowledging majority. In a three node cluster, two majorities must share at least one node, and that shared node carries the write forward. This eliminates lost acknowledged writes without any merging. The cost is real: every write waits for a network round trip, and if too many nodes are down to form a majority, the system stops accepting writes.

There is no configuration that provides low latency, high availability, and no lost acknowledge writes simultaneously. Every production system is a deliberate point in this spectrum.

Sharding, also called partitioning, splits data across nodes so that no single node must hold all of it. Where replication gives copies, sharding gives divisions. A sharded table assigns each row to a shard based on one column, the shard key. The shard key is a single choice that governs the whole table, not a per-query decision.

The shard key determines which queries are cheap and which are expensive. If the key is customer_id, then "all orders for customer X" resolves to one shard because those rows share a customer_id, while "all orders on date Y" touches every shard because those orders belong to many customers. If the key is order_id, then single-order lookups are cheap but "all orders for customer X" spreads across shards. No shard key makes all access patterns fast. Choosing one optimizes some queries at the direct expense of others.

A query that cannot be routed to single shard becomes a scatter-gather, or fan out: it sent to every shard, each shard returns it's matching rows, and the results are merged. If the query sorts or limits, the merge must reorder or re-slice the combined rows, because each shard only saw its own slice. Cross-shard queries therefore pay a latency and coordination cost that single-shard queries are not.
